## 1. Exact authority and supported product subset

The **first installed S4 command** supports only public **credential-free HTTPS** basic HLS VOD with finite media segments, one selected rendition, no encryption/DRM and no separate A/V mux. Existing `@xdownload/hls-vod-adapter` T009 flow remains sole Media/segment truth source under the same Core scheduler/journal/budget. Unsupported, authenticated, signed, live and credential-scoped manifests reject with typed evidence, not an opaque direct download or a synthetic success.

The upstream single effect command `EXECUTE_S4_SELECTED_HLS_VOD` remains the only S4 **acquisition-effect** command. A separate bounded Core-owned **metadata preview** operation is unavoidable if the user must see independently observed topology *before* confirming: this proposal defines a non-acquisition-effect `PREVIEW_S4_HLS_VOD` candidate operation. It must be independently reviewed as an explicit second 1.2 opcode rather than hidden in CLI, renderer or a side-channel. Preview fetches are real external **read effects** and must be budgeted/journalled before network; they create NO artifact, transfer work item, terminal or acquisition authority. This is a refinement to the #140 contract, not an existing capability.

The accepted Core seam minor for both S4-only opcodes is **1.2.0** (numeric parsed minor >= 2, not just major 1). Existing 1.0/1.1 operations keep their original semantics and peer permissions; old implementations refuse unknown opcodes. These S4 names do **not** activate reserved S3 confirmation/execute names. A 1.2 frame over caller-self-asserted legacy TCP peer MUST NOT gain authority; verify the OS session through an independently approved, deployed transport (Windows prerequisite #139 remains pending). A same-user/same-session OS token authenticates principal/session, **not human presence**.

## 2. PREVIEW operation and binding

**Input (closed, secret-free, exact):** `contractId`, `snapshotId` or a Core-owned preselection lineage reference as defined by T002, `requestedTargetId`, `manifestUri`, an immutable bounded permitted manifest-origin set issued by trusted installation policy (not task text), `expectedRevision`, `requestId`, `declaredTransferLimits`, and `selectedMediaProfileId`. Core validates user-facing origin intent (selected source) and OS session; accepts only a fixed public profile. Unknown fields including arbitrary headers, cookies, query tokens, media command strings and output paths reject before any effect. A preview is never a general URL fetch API: only narrowly typed .m3u8 with selected scope and explicit T009 parser.

**Core sequence:** accept metadata-only preview intent and budget reservation in its durable journal → invoke trusted T009 manifest port → record actual master/rendition declarations, their deterministic identity digest, chosen supported playlist topology, exact canonical manifest origin and bounded discovered rendition/segment origin graph in a Core-owned **preview record**. Record `previewId`, digest of canonical source/master/rendition declarations, profile id/revision/digest, offered rendition keys, observed graph, target/snapshot/revision, budget charged, OS session identity binding, creation and expiry. The immutable record is authoritative for *what was shown* but **not Target/Transfer/Format/Media PASS** and not proof segments are downloadable. Redact URIs carrying any potential secret before journal/logging; reject such URIs at admission, not merely redact after fetch.

The trusted installed CLI displays the exact observed source and each bounded supported rendition, including codec/resolution/bandwidth and a truthful unsupported marker. For display-only selection it uses Core-returned `previewId` and rendition key, not an independently reconstructed playlist from a browser page/model. If selected topology cannot be proven from a bounded fetch, return typed `INSUFFICIENT_EVIDENCE` or `UNSUPPORTED`; no confirmation or execution token is minted. **Preview may be stale**: manifest/master/variant/segment metadata re-fetched at execution must exactly bind the preapproval digest/identities or block and require a new preview/confirmation; never auto-swap.

The preview is bounded to one manifest + one selected media playlist during confirmation; no arbitrary site recursion, streaming live reload or unchecked CDN widening. T009 manifest budget applies before every fetch and is independently charged; preview bytes do not count as completed artifact bytes. A preview fault/restart preserves the pending/failed read truth without replaying already-accepted network effects blindly. Incomplete preview does not create an executable candidate.

## 3. User gesture, Core-minted challenge and durable confirmation

The installed CLI first displays the Core preview tuple `(installId,user OS session ref,contractId,snapshotId,targetId,previewId,manifest digest,selected rendition key,canonical origin graph,profileId,revision)` and explicitly requires confirmation. CLI must refuse with `NEEDS_USER_ACTION` in noninteractive/headless mode; timeout, EOF, cancellation and negative confirmation are typed refusal, never a default YES.

Core **mints** one opaque cryptographically random single-use `confirmationChallenge` bound to that immutable displayed tuple, registered peer connection/session, monotonic Core revision, an explicit short expiration (proposed <= 120s, implementation must pin clock skew and deterministic expiration), and the Core-preview record. The challenge is issued after preview and *before* the user click/TTY interaction. The renderer may echo it only after an explicit user affirmative gesture; Core checks a server-side pending-challenge record, exact tuple, TTL and OS session, consumes the challenge exactly once as an immutable journalled `CONFIRM_S4_SELECTION` metadata transition (name/codec still requires independent schema review), then admits the effectful `EXECUTE_S4_SELECTED_HLS_VOD` only from a durable confirmed record. Neither a displayed tuple hash nor an arbitrary `confirmed:true` field grants authorization alone.

**Threat scope:** an attacker already able to run code as the *same* OS user/session can simulate CLI text input; an OS-verified pipe + challenge cannot cryptographically prove human presence against that attacker. The v0.1 contract admits a user-operated local CLI under the same-user trust assumption, with a visible user gesture and positive session/challenge; it must not claim stronger user-presence guarantees. For stricter user-presence attestation, stop and require an independently approved OS trusted-dialog broker. Browsers, webpage scripts, AI and Recipes cannot present a CLI challenge as authenticated input or change the frozen scope. No untrusted surface may mint the challenge.

Store only a secret-free commitment/reference in durable logs; never log raw bearer challenge. On restart, a pending challenge is revoked; a **committed** confirmation can be reconstructed only with exact original preview/selection identity and freshness, but it does not authorize a *new* effect. Reconnect/session change cancels pending gestures; retransmitted identical confirmed execute request is an idempotent replay of its previous admission, never an independently new download. Once consumed, wrong contract/variant/snapshot/revision, changed target graph, expiry, replay, stale preview or post-cancel command must reject without effect.

## 4. Machine-testable URL/host graph and network security (public profile)

A user `--allow-host` value is only a **restriction/candidate**, not proof a CDN host was declared by the observed master/media playlist. Allowed effects are the intersection of (a) administrator/trusted-installation origin policy and (b) independently observed selected playlist provenance and (c) user-confirmed bounded delivery scope. Never treat a blanket wildcard, supplied website HTML, model claim or redirected final URL as playlist provenance.

Normalize every URL with the platform WHATWG parser; reject a raw string unless absolute, canonical and round-trippable under the declared grammar. Require scheme `https:`, no username/password, no query/fragment (including empty-but-present delimiters), no percent-encoded authority ambiguities, no encoded slash/backslash/NULL/dot-segment ambiguity, no IP-literal endpoints, no noncanonical default or nondefault ports unless the trusted installed origin registry explicitly pins that exact port, and no `localhost`/single-label/local suffix target. Define canonical IDNA/Punycode hostname + lowercasing, exact default port 443 canonicalization and a strict .m3u8 manifest path; reject if parsing or origin comparison is ambiguous. HLS-relative rendition/segment URLs resolve only against their **immediate signed-off parent playlist**; an origin change needs proof in the authenticated/observed graph and confirmed trusted-origin intersection. A segment URL is never authorized solely because it resembles an approved host.

For **every** manifest/rendition/segment request and **each HTTP redirect hop**, validate the candidate URL *before connecting*. Redirects are manual and counted within an explicit hop cap; refuse an undeclared host/scheme/port, HTTPS downgrade, changed URI provenance, new query tokens or HTTP Authorization need. DNS resolution/connection must block private, link-local, loopback, multicast, unspecified, cloud metadata and reserved IP classes (IPv4 and IPv6 including IPv4-mapped and DNS-rebinding transitions) per request; enforce that the actual connected address is among addresses checked for that exact destination and re-check on each new connection, not only pre-DNS hostname. If the platform transport cannot enforce resolved-IP connection pinning/peer TLS hostname while following redirects, **do not ship the public S4 HTTP adapter** and return typed `UNSUPPORTED_TRANSPORT`, rather than assuming string-only host checks are SSRF protection. Trusted localhost test fixtures must be explicitly flagged and unavailable to packaged production. No DNS answer, URL or browser-supplied content expands Core authority after confirmation.

Any unknown signed/secret-bearing query structure, auth challenge, HLS `EXT-X-KEY`, alternate audio, unsupported media topology or inaccessible content returns `AUTH_REQUIRED`/`UNSUPPORTED`/`INSUFFICIENT_EVIDENCE` as appropriate, never fallback to insecure direct HTTP or disable a required Media check.
