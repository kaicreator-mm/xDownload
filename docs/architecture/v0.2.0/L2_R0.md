## Drivers and invariants

- One business admission/state/effect/journal authority **per lineage**. K/DomainHarness controls newly K-admitted lineages; existing v0.1 Core continues to own old lineages until explicit reviewed cutover. Never open old and new writers on the same protected identity.
- Existing bytes/transfer budgets, digest, redirects, network confinement, browser auth and result projection are domain facts requiring preservation, not re-implementations of Kernel. No byte-stream crossing K.
- Discovery, user confirmation, output root, bounded membership and permission are immutable inputs to every operation. Model/recipe output is advisory.
- K permit is necessary but **not sufficient** to satisfy xDownload budget, redirect, digest and irreversible materialization rules.
- Default Node24 and pnpm monorepo, Woodpecker custom CI, Windows installed Host evidence for claimed Windows behavior. Preserve actual v0.1 platform matrix and not assume a desktop app exists.
- Only approved BUILD-selected static modules, public v0.10.3 exports, exact source/package-byte proof, no runtime dynamic discovery/import execution.

## Target control/data split

```text
existing CLI / Browser / optional desktop presentation
  -> Domain App façade (command/query/status, no authority)
  -> DomainHarness load/send/query/subscribe/stop
  -> selected K Primary: admission, effect permit, journal, replay, UNKNOWN
  -> selected S: deterministic recipe/selection and optional bounded advisory
  -> selected B: confirmed intent, scope and result semantics
  -> selected C: typed external Operation with Permit, no self-authorization
  -> trusted Node Host -> existing direct-acquisition / hls-vod / filesystem
  -> digest-backed materialized artifact and bounded typed terminal evidence
```

Use actual publicly exported BUILD: `@kaicreator/domain-harness-build` (buildV10App, projectSelectedComponents), `@kaicreator/domain-harness-contracts`, `@kaicreator/domain-harness-microkernel` (load/send/query/subscribe/stop), `@kaicreator/domain-harness-host-node`. C modules have module-level `externalEffect:true`; permitted external action must use the public selected-K effect gate. No invented Host CAS/API. The clean consumer must be separately proven on Node24.

## Critical architecture decisions / source-first Scaffold boundaries

- A01 (proposed; bounded writer succession): use **two small new packages** under existing `packages/*`, no separate repo, no second workspace, and no new lockfile authority. The **early T02 SDK/workspace bootstrap Task** (after T01 contract) exclusively creates both new package `package.json` files and only necessary additive root `package.json` / `pnpm-lock.yaml` dependency wiring, with real selected v0.10.3 public SDK + clean Node24 consumer evidence. Once T02 is independently reviewed, accepted, **merged into the integration base, and its active Builder Claim closed**, the later **T13 central BUILD/packaging Task** may exclusively update those same manifest/lock paths if actually required, and owns final public exports/build composition. T02 and T13 are **sequential writers, never simultaneous**; JIT Claims must bind exact current paths and base. No speculative root config edits or extra installer framework.
- A02 (proposed): typed confirmed job carries opaque `targetRef`/intent identity; trusted Host resolves approved locator and output path after K permit; raw URL/path are never an untrusted C config authority.
- A03 (required): classify old scheduler/ledger identity: owner partition by pre-existing frozen lineage vs newly created v0.2 K lineage. An explicit versioned migration must prove replay/rollback or permanently keep old lineages in the old runtime.
- A04 (required): existing direct adapter requires `TransferBudgetLedgerPort`; new application must show one authoritative budget reservation/consumption mapping without an independent private ledger. An in-memory fake ledger does not prove recovery. UNKNOWN/timeout may not create automatic duplicate effect.
- A05 (proposed): C effect adapter returns typed phase grammar; `accepted/running` are not terminal. A real digest-backed, checked output is necessary before success; Host filesystem durable file acceptance uses existing tested mechanism.
- A06 (proposed): version-specific selected K/S/B/C modules and public SDK sealed BUILD are immutable. Published v0.10.3 final package pin is a **later qualification checkpoint**, not a blocker to source planning.
- A07 (proposed): planning DAG lane separation puts S, Host direct, browser UI adapters and validation fixtures on different owned paths, then central integration after contracts and authority are settled.
