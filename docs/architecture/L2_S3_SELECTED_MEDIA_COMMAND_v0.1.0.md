# S3 selected-media Core execution authority — proposed narrow successor (v0.1.0)

**Owner:** #101 S3 Core/surface implementation, after #105 / PR #107 S3 architecture successor.
**Decision state:** REVIEW_REQUIRED; **not executable authority before exact-HEAD independent L2 adoption**. Do not mutate frozen Product PRD, original L2 or Task DAG. **Reuses** the reviewed S1 Core-owned intent/journal/control pattern (#103) and existing T008 Media port; does not silently extend S1 or S2.

## 1. Single concern and explicit API/version change

For **public, self-contained direct media file only**, permit a closed **two-step S3 authority pair**: `CONFIRM_S3_CANDIDATE` (durable, no effect) followed by `EXECUTE_S3_SELECTED_MEDIA` (durable effect intent), each gated on `xdownload.core-seam@1.2.0` (major 1). Existing wire kinds, response vocabulary, immutable contract and confirmed snapshot commands are unchanged. **1.1 is S1-only**: a 1.0/1.1 envelope attempting either new command fails `UNSUPPORTED_ENVELOPE_VERSION` before intent, work item or HTTP; an older Core lacking S3 rejects the unknown command/replay rather than reinterpreting it as S1/S2. Old 1.0/1.1 commands/queries remain accepted under their existing peer gates. Reopen an S3 journal with old Core is an explicitly unsupported downgrade; fail closed without side effects. Exact minor parsing applies to the S3 opcode, not only major-1 support.

**R1 review disposition:** F01–F03 independent P1 and F04–F06 P2 were received at PR #119 comment 6173625266. This successor revision defines explicit variant/user gesture binding (F01), per-hop public-URL guard (F02), non-authoritative caller digest (F03), canonical effect identity (F04), pinned Media probe semantics (F05), and existing-aggregate resume gate (F06). These are proposed normative fixes, not claims of implementation or independent acceptance.

This addendum is a **proposal to review**, not evidence that the command exists. Do not implement command from this unadopted document. Implement using separate, bounded Contract → Core → Shipped User Surface → Validation PRs; each change to authority requires exact-SHA review.

## 2. Selection and admission (no new discovery authority)

1. The installed browser or CLI presents the **explicit source and one chosen media variant**, including provenance/authorization context and applicable structural requirements. Auto selection is allowed only for an independently unambiguous supported candidate. Otherwise user confirmation is explicit; model ranking is untrusted recommendation, never evidence of file validity.
2. Core accepts a `SINGLE_RESOURCE` AcquisitionContract with `requestedScope.kind=single_resource`, continuation NONE and its original target identity. For this **initial S3 public CLI lane**, a `MemberId` is the **canonical variant-as-member identity** (one exact source+media-variant, never a page or loosely named video); a changed resolution, track selection or source means a distinct member and successor contract/snapshot. The existing `CONFIRM_SNAPSHOT` binds exactly this one selected `MemberId` and its `SelectionClaim`, contract, immutable scope and `authorizationContextRef`; **it does not contain a locator URL or prove that a user saw a variant**. The *new* `CONFIRM_S3_CANDIDATE` is required to bind the displayed selected URI+variant tuple to that already frozen member, independently of `CONFIRM_SNAPSHOT`. An arbitrary S3 candidate for a member not in the snapshot, a second selected variant, ambiguous source, stale revision or unverifiable currentness is rejected. Snapshot/member claims alone never establish download bytes or independent source truth.
3. For initial public-file S3, **the sole authorized CONFIRM peer is the installed local CLI** over its authenticated, same-user Core transport. Its explicit `xdownload media --url … --variant …` invocation is the user-selection event; the installed CLI must display the exact canonical `(contractId,memberId,variantKey,selectedLocator,mediaProfileId)` before confirmation, capture an explicit confirm gesture tied to this invocation and current Core revision, and send a **closed** `selectionAttestation` in the confirmation: `{kind:'EXPLICIT_CLI_GESTURE',interactionId,displayTupleDigest,confirmedAt,expectedRevision}`. `interactionId` is a unique locally generated nonce scoped to the authenticated CLI/Core transport and consumed exactly once; `displayTupleDigest` is a canonical hash of the displayed tuple, calculated by the trusted CLI from the same values as its Core command. Core verifies the digest against the candidate fields, `confirmedAt` freshness against its bounded clock policy, the expected revision and CLI peer/session identity; untrusted model/page/Recipe text cannot mint an authenticated CLI session/consumed interaction. The attestation is **user choice evidence only** and MUST NOT become independent Target/Media evidence. A privileged extension/Native Messaging gesture path is **not admitted** in this first public-file carrier; adding it needs its own gesture/transport contract and fresh review, not a browser page claiming a click. Automatic selection is likewise deferred until a separately verified deterministic AUTO rule exists. Wrong peer, reused nonce, stale/replayed gesture, mismatch between displayed tuple and submitted candidate or unauthenticated transport reject before recording intent.
4. The **metadata-only** `CONFIRM_S3_CANDIDATE` payload contains exactly `snapshotId`, `memberId`, `variantKey`, selected `locatorUri`, nonempty bounded `declaredRedirectHosts`, optional **untrusted** `byteConstraintSha256` (matching bytes required but never independent publisher evidence), optional total bytes / expected Content-Type, a **Core-registered supported mediaProfileId**, optional **additional** bounded media assertions and the mandatory `selectionAttestation` specified above. The Core obtains its mandatory MediaPolicy/structural validation from the pinned supported profile; the user/browser/model cannot author a weaker sufficient MediaPolicy, replace the required track/container list, or convert an unsupported profile into PASS. It binds the user-confirmed candidate to the *already confirmed* single selected snapshot member, contract, peer authorization and revision. Core verifies mediaProfileId against a versioned closed supported-profile registry (profile revision pinned in the intent) and commits an immutable secret-free candidate record **pinned to profile registry revision and content digest**, binding the selected source, Core-approved profile, extra assertions, user-confirmation provenance and selected member; it derives the canonical candidate identity from `(contractId,snapshotId,memberId)`. Confirmation cannot be synthesized from an untrusted page event or AI suggestion: the installed privileged surface must attest an explicit user action (or a separately proven unambiguous AUTO rule) over that exact displayed variant and authorization context. The surface supplies **no** trusted `candidateEvidenceRef`: the Core's durable candidate record is the sole reference, and is only evidence of user selection, **not** independent bytes/Target/Media validation. The **effectful** `EXECUTE_S3_SELECTED_MEDIA` payload contains only `snapshotId`, `memberId`; Core deterministically derives the single stable `effectId`, `workItemId` and `artifactId` from the accepted `(contractId,snapshotId,memberId)` and looks up exactly one approved candidate record to obtain the frozen locator/host graph and derive the pinned Core-owned MediaPolicy; extra assertions may strengthen but never weaken it. Missing/changed candidate, inconsistent snapshot, unconfirmed member, or second non-identical confirmation fails closed, never guesses a URI. Neither payload may carry raw cookie, bearer token, browser auth header, script, unrestricted URL expansion or arbitrary code. Unknown fields reject before journal; canonical effect/work/artifact lengths are checked before effects.
5. No new generic `download(url)` authority. A repeated identical confirmation converges only if its first attested nonce/tuple was already durably recorded; a different attestation or tuple under the same key is a conflict. Once an EXECUTE intent is recorded (including after cancellation or terminal), a second EXECUTE with any distinct request ID cannot create another effect/work item/artifact, debit another budget, or start another HTTP request; ordinary recovery operates on the prior durable intent only. No caller-supplied artifact override exists. S1 payloads never become S3 merely by attaching `mediaPolicy`; S3 never bypasses its confirmation. A changed selection or detected changed representation requires an explicitly new successor contract/snapshot and candidate confirmation, not a silent payload rewrite. `CONFIRM_S3_CANDIDATE` must never treat a selected URL/MediaPolicy as independently validated truth.

### 2.1 R2 F01 — protected installed Core session

The legacy loopback seam and caller-supplied PeerIdentity are NOT OS-verified installed CLI identities. S3 1.2 commands MUST reject on that transport even if an envelope asserts surface=CLI. The caller-generated interactionId and displayed tuple digest are correlation values, NOT Core evidence; these rules take precedence over weaker wording in Section 2.

1. An installed Core host exposes a protected local-only session transport: a Windows named pipe with owning-user/logon-session DACL and server-verified connecting token, or a POSIX 0600 Unix socket with OS peer UID verification. Core derives actual user/session identity from the OS connection, never envelope fields. Browser, old loopback and Native Messaging transports cannot claim S3 1.2. Without this capability S3 fails UNSUPPORTED. This is a same-user local trust model; a malicious process already executing with the same OS user is outside the stated trusted-user boundary, not falsely claimed cryptographically impossible.
2. Core issues one cryptographically random, short-lived, single-use interactive challenge BOUND TO the authenticated transport session, current Core revision, and exact canonical displayed (contractId,snapshotId,memberId,variantKey,selectedLocator,mediaProfileId) tuple hash. The installed CLI displays that exact tuple, requires an interactive attached-TTY confirmation (no --yes, redirected stdin or page/Recipe auto-confirm), then returns the CORE-ISSUED challenge. Core consumes challenge atomically with candidate journal commit. A self-minted nonce, tampered tuple, reconnect, duplicate, expired challenge, different OS user/session or changed revision cannot confirm.
3. Required installed negatives: raw localhost client declaring CLI; forged self hash/nonce; noninteractive/headless CLI; unauthorized user; page/Recipe proxy; reconnect/replay; swapped variant/URI/profile; and a positive real interactive installed CLI gesture. If protected identity cannot be verified S3 stays disabled; a stronger OS human-presence guarantee requires a separate reviewed capability.

### 2.2 R2 F02 — closed Core-owned public source policy

S3 public-file positive admission requires a Core-approved immutable PublicMediaSourceProfile version 1 provisioned from trusted installation configuration OUTSIDE task, HTML, CLI command payload, model or Recipe. The pinned profile contains a finite list of EXACT HTTPS origin tuples (scheme, lowercase host, explicit port), plus separately declared exact redirect-CDN origin tuples. No wildcard, suffix matching, implicit DNS or caller expansion. A specific fixed-port http://127.0.0.1 origin is allowed only in controlled test profiles, never an unbounded production exception.

Core checks the frozen profile ID, revision and SHA256 content digest, exact approved origin and ASCII path grammar on initial and EVERY redirect destination BEFORE its next HTTP request AND BEFORE persisting or logging that locator. The grammar is: ^/media/[A-Za-z0-9_-]{1,64}\.(mp4|m4a|mp3|webm)$. Both raw and normalized paths must satisfy it. Any percent escape, dot segment, repeated slash, extra component, unknown extension, Unicode, userinfo, query, fragment, HTTPS downgrade or unlisted origin is UNSUPPORTED. This excludes opaque signed paths deterministically rather than guessing that a query-free URL is public. The existing T008 host-only redirect check is NOT sufficient; apply this pinned source policy in addition to it on each hop. S3 public mode has no locatorRefresher and no fallback to S1, S2 or a broker. Changed/missing source profile on replay fails closed.

QA positives under an explicitly trusted test profile: https://media.example.test/media/clip_01.mp4 and an approved redirect to https://cdn.example.test/media/clip_01.mp4. QA negatives: /clip.mp4, /media/t0.mp4?token=x, /media/%63lip.mp4, /media/clip_01.mp4#x, /media/clip_01.mp4/extra, userinfo, unknown host, unknown profile, redirect to an undeclared CDN or HTTPS downgrade. Example hosts are NOT installed default origins. Approved transport provenance grants only PROBATIVE Target evidence, never independent publisher identity or Media validity.

## 3. Execution, truth and hostile examples

Core reads the preceding Core-journaled immutable candidate record, journals accepted S3 execution intent and its canonical effect/artifact identity **before** external effects, registers exactly one Core-owned lineage/work item and reserves transfer budget, and dispatches **only** `DirectHttpAdapter` with `slice='S3'` and declared provenance-bound public locator. The single T015 scheduler/writer and frozen T007 projector own acceptance/terminal facts. Never return COMPLETE from command ACCEPTED or HTTP 2xx.

Every required layer — Target, Transfer, Format, **Media** — passes independently. Core derives the **non-waivable** required Media checks from the approved pinned profile; caller-supplied checks are only additive. A profile with missing, unsupported or invalid structure probes is UNSUPPORTED/FAILED even when its client-chosen signature happens to match. This closes the circular-oracle path in which an untrusted source could define one trivial matching signature and then self-certify a different or corrupt track. A missing/empty MediaPolicy returns a typed negative `MEDIA_POLICY_REQUIRED` / `MEDIA_INVALID` (PR #118 is proposed precursor), not vacuous PASS. Existing static byte-signature validation by itself is **not sufficient** for all real media containers/tracks; before claiming support for a container, a bounded structural probe must validate its promised properties. Initial supported format subset must be named and proven by fixtures (e.g. self-contained MP4 with required A/V track presence, or standalone audio). Ambiguous mux/codec topology, separated A/V, DRM and unknown tracks are UNSUPPORTED; do not invent success, auto-mux or download wrong files. Structural Media rejection may accompany otherwise valid digest; it still blocks acceptance. The caller-provided `byteConstraintSha256` is a byte-integrity constraint only: it may reject a mismatch but **never yields `PUBLISHED_SHA256/DECISIVE`** even if bytes match. Initial public S3 therefore uses `REQUESTED_LOCATOR_PROVENANCE/PROBATIVE` for successfully bound selected target, or UNKNOWN/BLOCKED if the selected provenance is not proven. A future DECISIVE branch requires a *separate* trusted and immutable publisher-evidence record with verified provenance, captured and identity-bound **before** transfer, plus a separately reviewed read-only Core evidence port; no such port is authorized by this addendum. Durable candidate and Target-witness records pin the basis and prohibit replay-time reinterpretation as independent proof.

**Public URL admission is deliberately narrow:** this v0.1 public S3 lane accepts only credential-free HTTP(S) URLs with no username/password, query string or fragment, no authorization headers and no broker-managed session provenance. Eligibility is not inferred from a query-free URL alone: the installed CLI must classify the canonical normalized URL as an explicitly selected, reachable credential-free public file under the currently authorized session-free profile. Opaque unknown path/token structure, encoded credentials, percent-encoded query delimiters, and known tokenized/signed locator patterns are conservatively `UNSUPPORTED`; if the source cannot be conclusively classified public, stop without exporting the URI to Core. A URL with query parameters (including apparently benign cache parameters), credential-bearing path/known signed-locator provenance or unverifiable public classification is UNSUPPORTED before journal or HTTP; do not transmit a credential-like URI to Core or logs. A separately reviewed privileged broker contract handles session-bound/CDN-signed paths. **The same strict canonical URI eligibility guard runs for every `Location` redirect and any candidate refreshed locator BEFORE the next HTTP request and BEFORE inserting that locator into Core's journal, ledger, receipt or log**; the T008 host-only redirect check is insufficient and must be wrapped/hardened by the S3 Core adapter. Each allowed redirect must both preserve the declared host provenance and pass the public credential-free eligibility guard; ambiguous hop fails as typed unsupported/auth-boundary evidence, never follows or persists it. S3 public mode forbids `locatorRefresher` and has no fallback to S1/S2 or broker. This reduces initial URL coverage rather than guessing whether a query is an expiring bearer secret.

**Replay pin:** immutable confirmation binds exact supported media profile registry ID, revision and content digest **and the structural probe implementation/semantics revision**. A successful Media check commits a canonical Core-owned durable Media witness with input artifact digest, profile and probe semantic version and applicable results. Reopen/upgrade must use byte-identical mandatory checks and compatible validator/probe semantics, or reuse the original immutable witnessed result for already durably accepted bytes; otherwise fail closed and fence reevaluation, never silently use current defaults. User-supplied assertions only tighten. A profile semantic change requires explicit new confirmation/successor snapshot; old Core lacking this profile cannot mark Media PASS.

Core stores staged bytes and actual artifact digest, issues one terminal from durable evidence and retains restart/idempotency/late-cancel precedence. Crash before witness/terminal must re-derive truth from durable outcome and owned evidence, not repeat external I/O or replenish budgets. Attempts with auth-required/browser-bound signed resource are **not** in this public-file lane.

## 4. Browser-session media: separated prerequisite, never a shortcut

For an authenticated, session-bound or expiring media locator, **STOP this command before external HTTP** and require a separately reviewed, scoped privileged broker byte-delivery contract with origin, authorization partition, selected member, snapshot, host/redirect graph and expiry. Browser cookies/tokens and reusable signed URLs stay in the broker, never Core/CLI/model/Recipe/logs. Broker returns secret-free bytes/provenance only. Core still owns all Media validation and artifact acceptance. Existing S2 delivered-byte handoff cannot be relabeled S3 unless the S3 structural/selection authority is independently reviewed. Do not claim browser-authenticated S3 is supported because public S3 passes.

## 5. Closed preflight and negative matrix

- **Fresh-task capability**: the CLI uses a read-only, same-transport, correlated, fresh-aggregate `READ_PROJECTION` probe (legacy 1.0 query) and requires a valid response from Core schema >=1.2.0, major=1, *exactly* the expected AGGREGATE_NOT_FOUND rejection, as in #103 §2.1. Any 1.0/1.1 Core, existing aggregate PROJECTION, peer denial, fence, mismatch, malformed response or timeout stops before contract, work item and HTTP.
- **Existing-task resume (NOT fresh-task probe bypass)**: an already registered 1.2 aggregate returns `PROJECTION`, not `AGGREGATE_NOT_FOUND`. CLI first authenticates to the *same* Core transport, verifies actual schema >=1.2.0, `inReplyTo`, exact aggregate/contract/snapshot/candidate/peer authorization context and current revision from the Core's read-only projection, then rebinding uses the existing previously committed candidate+effect record and durable work-item state. It may read status or reconcile an accepted in-progress intent; it **cannot** create another confirmation, execute, effect, budget or HTTP request from a projection alone. A mismatched identity/revision, missing intent, incompatible profile/probe version, stale peer or recovery fence fails closed; a genuinely changed request requires a new successor contract and fresh interactive confirmation.
- **Scope/identity**: wrong/unselected variant or displayed tuple, missing/changed Core-owned candidate record, wrong snapshot/member, host expansion, old revision, reused selection nonce, replayed/stale click, repeated execute after terminal (different requestId), cross-user peer, stale selected evidence → fail closed; no new scope or second network effect.
- **Media/integrity**: no Core-approved profile, caller-chosen permissive signature attempting to waive mandatory profile checks, missing/invalid MediaPolicy, a bogus signature, required track absent, corrupt container, HTML login disguised as video, untrusted byte constraint mismatch or forged publisher-digest claim, oversized/truncated transfer → failed/unsupported Media/Format/Target as appropriate, no accepted artifact, no falsely COMPLETE terminal.
- **Durability**: kill before/after intent commit, after partial bytes, between scheduler outcome/Media witness and terminal, cancel before/during/after accepted bytes, exact replay, profile probe revision mismatch and old-Core downgrade → no repeated transfer/budget, no accepted false truth, correct frozen stop/result tuple.
- **Security**: unbound cookie/token, URI username/password/fragment, query-bearing or potentially signed locator presented as public, supplied browser headers, undeclared redirect, revoked browser auth, arbitrary model-proposed URL and untrusted extension commands → fail closed, no secret echo or automatic fallback to another lane.
