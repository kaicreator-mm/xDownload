## 1. Scope and preserved authority

This additive successor covers **one missing execution carrier**, not a new product, generic gateway, crawler, Desktop shell, or modification of frozen Product semantics. The canonical AcquisitionContract remains immutable and keeps its closed field schema. The Core is the sole authority for contract/snapshot/selection scope, identity, budgets, cancellation cutoff, ledger, recovery and the multidimensional terminal projector. CLI, browser and Desktop remain thin adapters. The existing browser-only `EXECUTE_S2_ACQUISITION` and its auth, chunk and provenance restrictions remain unchanged.

The currently packaged CLI `SUBMIT_CONTRACT` is an **acceptance**, not an executable download. Contract fields cannot encode the direct locator/redirect identity. Therefore, an explicit narrowly typed execution carrier after contract acceptance is justified, subject to review.

## 2. Proposed S1 seam carrier (T004 successor)

- Proposed command: `EXECUTE_S1_DIRECT_ACQUISITION`, peer surface `CLI` only, for an *already durably accepted* contract with `intentType=SINGLE_RESOURCE` and `requestedScope.kind=single_resource` (distinct frozen identifiers, PRD §§10, 28), at the expected revision and immutable requested target/scope.
### 2.1 Exact command schema/compatibility decision (F06)

**Proposed new wire schema identity:** `schema=xdownload.core-seam, version=1.1.0` (the existing pre-S1 schema is `1.0.0`; DomainContracts schema version is independent). Preserve the existing three envelope kinds, typed response vocabulary (`ACCEPTED | REJECTED | PROJECTION`), `READ_PROJECTION` query and the unchanged S2 command. `EXECUTE_S1_DIRECT_ACQUISITION` is the **only** newly admitted opcode in minor 1.1. The proposed implementation MUST update `CORE_SEAM_SCHEMA_VERSION` and gate this opcode on request version **at least 1.1.0, major=1**; current major-only parsing is insufficient for this command. Other already-published 1.0 operations may retain 1.0 wire inputs under the frozen peer/scope security checks, and 1.1 responses retain the existing closed response shape.

**Paired deployment and fail-closed combinations:**

| Caller/Core pair | Required behavior |
|---|---|
| Old CLI 1.0 / new Core 1.1 | Existing commands/read queries only; new Core accepts and returns typed 1.1 responses; no S1 execution magically occurs from a submitted contract |
| New CLI 1.1 / old Core 1.0 | CLI MUST first run the existing, read-only `READ_PROJECTION` query on its own aggregate and inspect `response.schemaIdentity.version`; a 1.0 response or missing/malformed response means S1 unsupported: abort **before** SUBMIT or network transfer, with an actionable Core-upgrade diagnostic. Never try the S1 command optimistically |
| New CLI 1.1 / new Core 1.1 | Read-only preflight confirms exact `xdownload.core-seam` supported version; S1 command is admitted only after immutable contract submission and the normal identity/peer gates |
| Old Core 1.0 against durable 1.1 command journal | Unknown command and incompatible durable schema MUST fail closed on reopen; never skip, drop or reinterpret the journal entry and never fabricate terminal truth. Downgrade of a data root containing S1 intents is unsupported; backup/restore/upgrade guidance is mandatory |
| New Core 1.1 reading old 1.0 journal | Deterministic replay of prior canonical commands and revisions under old behavior; no implicit S1 side effects or reinterpretation. New 1.1 journal entries replay only after 1.1 schema/command validation |
| Major≠1, invalid version, new S1 command under 1.0, or mixed-version replay conflicts | Reject with typed `UNSUPPORTED_ENVELOPE_VERSION` or `UNKNOWN_COMMAND_TYPE` as applicable before intent/work-item/network; preserve durable root, do not fall back to S2 or HTTP direct from CLI |

This is a **required implementation delta in #101 PR #102**, not a claim that existing code already implements feature gating. The binary package for a claimed S1 platform tuple must install CLI and Core as one tested 1.1 pair. Focused T004/CLI/Core tests: preflight query against 1.0 Core, 1.0/1.1 input acceptance matrix, opcode under 1.0 rejected before effects, 1.1 acceptance/projection, malformed response, journal downgrade hard fail, older journal forward recovery, mixed command-version request replay and schema/response unchanged. An incompatible peer can never earn Product PASS just because the major remains 1.

### 2.2 T008/T007 adoption prerequisites and exact projector facts (F07)

The three result tuples below are **normative successor targets**, not assertions about the old release baseline's ability to project them. To realize them while keeping one T007 Core projector and no self-certification, the implementation PR must close these **separate named dependencies before installed-path approval**:

1. **T008 optional publisher-digest validation:** change the direct-transfer request/decoder/adapter to admit an omitted publisher SHA without treating a self-computed artifact hash as Target oracle. Validate selected URI and every authorized redirect edge, real length/range Transfer and applicable Format, and produce a typed `REQUESTED_LOCATOR_PROVENANCE` / `certaintyClass=PROBATIVE` Target result. A separately supplied publisher digest that mismatches yields `DIGEST_MISMATCH`; no acceptance. This is implemented in proposed PR #102 but must be independently source/host verified at its **current exact HEAD**.
2. **T007 resolution-vs-acceptance separation:** the old projector resolves S1 Target only when `acceptedSelectedMemberIds` contains the member; a failed validation cannot then yield `RESOLVED`. Add a **bounded, durable, independently supported** S1 requested-target-resolution fact, distinct from downloaded/accepted work-item membership. A proven selected URL identity can be `RESOLVED` even when bytes fail required validation, but this does not imply accepted acquisition or fulfilled request. Reject a fabricated resolved fact, mismatch to frozen requested identity, missing provenance or mutable after-the-fact inference. The Target validation registry and accepted-ledger gates remain mandatory.
3. **T007 provenance-unproven blocker/fulfillment derivation:** the previous `blockedBeforeAnyResolution.reason` is limited to `AUTH_FAILED | AUTH_REQUIRED | UNSUPPORTED` and the old `requestFulfillmentFrom` makes all blocked facts `UNSATISFIED`. Add an **explicit S1 Target-provenance-unproven fact path**, distinguishable from auth/unsupported, to derive tuple (b) `UNKNOWN/BLOCKED/FAILED/NOT_APPLICABLE/VALIDATION_FAILED` after attempted transfer (or `NOT_STARTED` when no transfer). This is not a license to change the meaning of unrelated collection, S2, cancellation or auth tuples. Proof must be grounded in durable Target failure evidence and independently reviewed; the Core projector alone constructs the public terminal.
4. **Tests/rollout gate:** add table-driven T007 and T008 negatives for (a) ordinary URL-only successful artifact without publisher SHA, (b) no trustworthy Target provenance, and (c) externally published hash mismatch with Target RESOLVED but no accepted artifact, plus no double-charge, cancellation-before/after-commit, replay after SIGKILL, torn ledger, schema mismatch and S2/CJ regression. Assertions must check all five tuple dimensions, `ValidationSummary`, evidence basis/certainty, and accepted ledger bytes **on the same Core source**. Do not assert closure from unit-only fixtures or fabricated acceptance. **If the current PR #102 does not implement these required projector paths, its S1 Product journey and #101 stay BLOCKED; make a separate minimal T007 concern PR if necessary, with its own exact-SHA review, instead of silently weakening the tuples.**

These scoped successors amend only the **required implementation/evidence paths** under review; frozen Product Result enums and the single Core authority remain unchanged. A proposal-level schema choice here does not itself authorize an unreviewed wire change.

- Bound payload: canonical `snapshotId`, `memberId`, `artifactId`; `delivery.locatorUri` (http/https only), `declaredRedirectHosts` (at most 8 plain hosts, each at most 255 characters, including the selected URL host; CLI constructs this bounded set from the user-selected URL host plus only hosts the user explicitly authorizes using `--redirect-host`; no page inference), optional independently-sourced `expectedSha256`, optional `expectedContentTypePrefix` and `expectedTotalBytes`. Closed keys and byte/identity limits, explicit rejection of raw credentials/tokens.
- The **user-facing normal flow takes a URL**, not a SHA. An independently published digest may be used as an optional *strengthening* input. Internal artifact SHA256 is required for durability/integrity, but its computation *after downloading* is never proof that the resource matches a distinct, pre-registered byte identity.
- Target proof has **two explicitly different certainty bases** in PRD §20 `RESOURCE_IDENTITY` evidence (required `confidence_or_certainty_class`, `source_identity/provenance`, `independence_from_discovery`): `PUBLISHED_SHA256` only for a separately sourced publisher digest fixed before transfer; `REQUESTED_LOCATOR_PROVENANCE` for the user's explicitly selected URL plus every actually traversed, authorized redirect edge. The latter proves which bound URL/resource was acquired, **not independent byte-version equivalence**. Under the frozen T002 evidence contract, `confidence_or_certainty_class` is serialized as `certaintyClass`, restricted to `DECISIVE | PROBATIVE | SUGGESTIVE | INSUFFICIENT_EVIDENCE`; `REQUESTED_LOCATOR_PROVENANCE` is the basis string in `provenance.sourceIdentity`, **never a new certaintyClass enum**. A no-digest provenance-only Target record MUST use `certaintyClass=PROBATIVE`, whereas a separately verified published SHA can use `DECISIVE` when byte equality really holds. Internal SHA256 is only a durability/integrity fact. Do not use self-hash as a publisher oracle (C34).
- **Pinned no-digest result tuples (frozen PRD §§16,18.1,20,22):**
  - **(a) Valid requested locator/provenance binding, no undeclared redirect, all applicable Target (provenance), Transfer (length/range), Format layers passed and accepted bytes:** `RequestFulfillmentStatus=COMPLETE; TargetResolutionStatus=RESOLVED; SelectionAcquisitionStatus=COMPLETE; CoverageStatus=NOT_APPLICABLE; StopReason=NONE` (PRD §18.1). `ValidationSummary.status=ALL_PASSED` refers only to **the actually applicable and checked layers**, including the provenance-bound Target claim; the Target evidence must encode `provenance.sourceIdentity=xdownload/target-validator:REQUESTED_LOCATOR_PROVENANCE` and `certaintyClass=PROBATIVE` (frozen T002 enum), not a `PUBLISHED_SHA256` byte-identity claim or `DECISIVE` provenance-only assertion. `ALL_PASSED` is the T007 result/projector validation-summary vocabulary, **not** an extra PRD §16 status. External task/human acceptance remains subject to independent hidden pre-exposure Oracle verification.
  - **(b) Target provenance is unproven (missing user selection, undeclared/ambiguous redirect, unbound target, or no reliable requested-locator fact) after transfer attempted:** `RequestFulfillmentStatus=UNKNOWN; TargetResolutionStatus=BLOCKED; SelectionAcquisitionStatus=FAILED; CoverageStatus=NOT_APPLICABLE; StopReason=VALIDATION_FAILED`. Target layer fails, `ValidationSummary.status` cannot be `ALL_PASSED`; the bytes are not accepted as a validated artifact. If no transfer was attempted, `SelectionAcquisitionStatus=NOT_STARTED`, preserving the rest of the blocked/unknown truth.
  - **(c) Separately supplied, independently published SHA differs from delivered bytes:** `RequestFulfillmentStatus=UNSATISFIED; TargetResolutionStatus=RESOLVED; SelectionAcquisitionStatus=FAILED; CoverageStatus=NOT_APPLICABLE; StopReason=VALIDATION_FAILED`; Target layer `DIGEST_MISMATCH`; `ValidationSummary.status` cannot be `ALL_PASSED`. No COMPLETE or accepted validated artifact.
- These rules use **only** frozen PRD §16 statuses; `NOT_VALIDATED` is **not** a status enum and must not appear in normative result tuples. Fail closed when provenance cannot be proved rather than inventing a new enum. Test-frozen external Oracle remains off-surface and independent.
- Source or test fixtures cannot promote their own observed result into target truth; P1/C09/C34 counterexamples remain required. If no additional redirect hosts are supplied, the bounded set contains **only the selected URL host**: zero redirect hops are allowed to an unlisted host; any hop (including cross-origin/CDN) landing on an undeclared host fails closed. Empty authorized-host input must never grant arbitrary redirects (normalize to selected host or reject rather than widen).
- An accepted command **journals durable execution intent first**. Only after COMMITTED does Core create a canonical durable work item / dispatch intent, and **that work-item/dispatch fact MUST be durably committed before the first external network byte or HTTP request** (frozen L2 §6.3(5)). If work-item allocation/commit fails, no network I/O starts. Failure or UNCERTAIN journal durability fences the authority before any external effects. Completion is recorded via Core-private port from durable facts and the single projector; neither command ACCEPTED nor HTTP 200 means final success.
- Replay rebuilds accepted identities and per-command revisions, never starts transfers during authority reconstruction. A crash after command COMMITTED but before work-item materialization reconciles from the durable command intent and does not infer that an external effect occurred. Post-composition reconcile classifies work items/artifacts from durable state. Accepted artifacts are never re-downloaded, re-charged or re-accepted. Missing, corrupt or torn durable facts fail closed with truthful classifications. Pending work needs bounded recovery visibility; never silently wait forever for restart to expose a failure.

## 3. Negative/acceptance matrix

| Case | Expected gate |
|---|---|
| Unknown command field / malformed schema | Reject before intent |
| Non-CLI S1 peer, foreign install/user, raw secret | Reject; no new privilege |

| Missing optional publisher SHA | Normal URL input admitted; Target validated on explicit URL/redirect provenance (sourceIdentity basis `REQUESTED_LOCATOR_PROVENANCE`; certaintyClass `PROBATIVE`), never on a post-hoc byte oracle; successful tuple is frozen PRD §18.1 only after all applicable layers pass |
| Known SHA differs from acquired bytes | Failed/unknown terminal, never COMPLETE |
| HTML login masquerade, truncated/range conflict | Failed/partial/unknown; no artifact acceptance |
| Duplicate request ID same payload | Convergent replay; one work item and charge |
| Duplicate ID changed payload or late terminal command | Reject without side effects |
| Cancel-before-accept and accept-before-cancel | Existing Core precedence unchanged |
| Crash after intent COMMITTED/before work item | Safe deterministic reconcile or truthful pending/failure |
| Crash after accepted bytes; corrupt/missing file; torn ledger/journal | No duplicate transfer or budget; fail closed/recovery truth |
| Target provenance itself unproven | Frozen tuple UNKNOWN / BLOCKED / FAILED / NOT_APPLICABLE / VALIDATION_FAILED (or NOT_STARTED when no transfer); do not mint new status values |

## 4. Explicitly deferred carriers

S3 direct-media inherits relevant direct-transfer ports but **requires additional Media validation and user-selectable media identity**. S4 HLS remains a distinct manifest/segment/assemble validator, never coerced to one opaque direct URL. S5 defaults to current-page frozen membership and `continuation_scope=NONE`; S6 follows only an explicitly confirmed finite/natural-end collection relation. Each S3, S4, S5 and S6 execution/selection carrier requires its own **named, exact-SHA independently reviewed L2 successor authority decision** before implementation dispatch; only then may bounded Core and shipped-user-entrypoint PR slices be developed in separate worktrees. The S1 approval by #103 cannot serve as authorization for S3–S6 commands. This addendum does not pre-authorize arbitrary new opcodes or changes to browser credentials or continuation authority.
