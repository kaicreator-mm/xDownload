## 1. Architecture objective

Complete the v0.2 Domain App migration at installed user-facing boundaries while keeping the already-qualified component architecture and the frozen v0.1 semantics intact. Prefer reusing existing packages, tested operating-system capabilities and the existing Core/Host seams over new frameworks or duplicated business logic.

## 2. Authority and data flow

```text
Desktop renderer / CLI / Browser extension
  -> thin surface adapters (no lifecycle truth)
  -> ONE local Core process / existing Core seam
       -> old Core owns pre-existing v0.1 lineages
       -> DomainHarness Domain App/K owns newly admitted v0.2 lineages
  -> one lineage-owner selector; never two writers for one lineage
  -> for K-owned work: K admission + Effect Permit + Journal + recovery/UNKNOWN
  -> S/B deterministic recipe, confirmed intent and finite selection
  -> C external Operation
  -> trusted Host -> existing direct-acquisition or HLS adapter
  -> confined partial file -> validation -> atomic materialization
  -> authoritative status/result projection
```

Invariants:

1. One authoritative business-state/effect writer per lineage. Old v0.1 lineages remain old-Core-owned unless a separately reviewed migration explicitly transfers them; new K lineages must not be writable by the old owner.
2. The DomainHarness K owns admission, permits, Journal and its state semantics. Existing transfer and HLS code remains the data plane; high-volume bytes do not pass through K.
3. A Permit is necessary but not sufficient: xDownload still enforces scope, target identity, redirect policy, budget, output confinement, integrity and materialization rules.
4. UI and CLI render authoritative projections. They do not invent completion, ETA, retry eligibility, file identity or UNKNOWN resolution.
5. SDK source identity is the exact DomainHarness Git tag commit `061376f4a023070f215f9feffad5c24d96d503cb` (tree `099cdc831aef63befd62aaede7e7a853d1be468f`). The selected public SDK tarballs from that tree retain internal package-manifest version `0.10.2-rc.0`; the v0.2.0 platform receipt records 4/4 SHA-256 matches against the #183 source-build receipts. `v0.10.3` therefore names the source tag, not an npm-published package version. Use public package-root exports and byte/hash evidence; no internal paths, registry fallback, silent re-pack/rename or unreviewed SDK patch.
6. Any malformed user intent must be rejected by the trusted pre-send gateway before public `DomainApp.send`; the rejection must not poison the Effect Journal. This is a consumer-side guard for the known upstream boundary, not a claim that upstream issue #1437 is fixed.

## 3. Single-process integration and lineage routing

The v0.2.0 packages are components, not permission to start an independent Kernel in every surface. v0.2.1 must integrate the selected Domain App into the existing single local Core process and route commands through the existing Core seam/Native Host boundary.

- Load/own the DomainHarness K runtime once in the Core process. Do not instantiate K separately in the CLI, Electron main process, or Browser Native Host.
- Keep old v0.1 lineages on the existing Core scheduler/ledger; route only newly admitted v0.2 lineages to K. The lineage-owner selector is explicit, fail-closed on ambiguity, and never lets both owners write one lineage.
- The new K path uses its existing Journal/FileCasDocStore semantics inside that one process. Cross-process SQLite CAS remains NOT_PROVEN; no architecture statement may imply it is solved.
- All surfaces remain thin adapters. Desktop main uses the existing Core lifecycle/start binding and seam client; the renderer has no direct K, Host, filesystem, or network authority.
- The core integration task must prove old-lineage behavior is unchanged, new-lineage work reaches K exactly once, restart reopens the same owner, and a conflicting owner refuses before an external effect.

## 4. Desktop shell candidate

**Candidate choice: Electron 45.1.0**, because the current workspace and Host are TypeScript/Node based and the desktop package is currently an adapter rather than a packaged shell. The official release listing dated 2026-10-27 reports embedded Node.js 24.22.1, compatible with the project’s Node `>=24` runtime line; this exact candidate still needs a pinned dependency, security review and packaged smoke. See [Electron 45.1.0 release metadata](https://releases.electronjs.org/release/v45.1.0). This avoids introducing a second application-language toolchain. Do not use a floating Electron version.

Security requirements:
- renderer loads packaged local assets only; no remote website is loaded into a privileged renderer;
- `nodeIntegration=false`, `contextIsolation=true`, `sandbox=true`, restrictive Content Security Policy;
- preload exposes a narrow, typed allowlist only; no raw filesystem, shell, process, network, arbitrary IPC or Host authority is exposed to renderer content;
- validate IPC sender and every payload; disable arbitrary navigation/window creation; no secrets in renderer storage or logs;
- only the trusted main/Host boundary talks to the existing Core seam and filesystem APIs;
- keep UI presentation separate from Core lifecycle, download policy and result truth.

Official references for the candidate decision: [Electron process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Electron security checklist](https://www.electronjs.org/docs/latest/tutorial/security), [Electron distribution overview](https://www.electronjs.org/docs/latest/tutorial/distribution-overview). A review or test failure that invalidates the security model blocks freeze; it must not be waived for schedule.

### Existing Core lifecycle and single-instance authority

The current install binding already exposes a per-user `coreStartPath` and a reproducible single-Core start script in `build/install-host.ts`. The desktop main process must reuse that existing install/Core lifecycle boundary and the existing Core seam; it must not instantiate a private Core/Kernel, create a second scheduler/ledger, or invent a second IPC route. Startup must verify the expected install/user identity and configured pipe/seam target. The package/Host task owns installation and readback of the existing start binding. If the packaged shell cannot use this contract safely, stop before expanding the UI and request an L2 amendment.

## 5. Transfer, queue and recovery policy

- Preserve one state owner per lineage: the existing Core scheduler/ledger for old v0.1 lineages, and DomainHarness K/Journal for newly admitted v0.2 lineages. Do not let both owners write one lineage or add a second queue database/private UI ledger.
- Retry only classified transient failures, within the existing lifecycle budget and a finite attempt/time bound.
- UNKNOWN is not a retryable failure. Reconcile the authoritative operation first; if the outcome cannot be proven, report UNKNOWN and require a safe successor decision.
- Resume partial transfers only if byte-range support, a stable remote validator/identity, expected partial length and local partial-file identity all match. If any predicate is missing, do not append blindly.
- Download into a confined temporary/partial path. Verify applicable digest, length and content policy before atomic finalization. Never default to overwriting an existing file.
- Sanitize suggested filenames; reject path separators/traversal and reserved/invalid names; treat remote filename headers as untrusted display metadata.
- Progress values derive from actual transferred bytes and authoritative lifecycle state. Unknown total size yields no fabricated percentage/ETA.
- A user retry creates a distinct attempt identity linked to the prior attempt; it does not rewrite prior terminal truth.

## 6. Surface contracts

### CLI
- Preserve the existing JSON output contract and documented exit codes for machine automation.
- Add an explicit human-readable mode and progress on stderr; JSON stdout remains a single valid document when JSON mode is selected.
- Add a local diagnostic command for runtime, Host connectivity, destination writability and version/build identity.
- No automatic Core start/stop or fallback transport that changes the trusted boundary.

### Browser extension
- Keep Manifest V3 and current user-gesture flow.
- Ask for host permissions only at the action that needs them; show the target and permission rationale.
- Keep cookies/auth context opaque and local; no raw credential transfer into K, model prompts, or logs.
- Missing Host, permission denial, origin mismatch and invalid payload fail closed with actionable feedback.

### Desktop
- The minimum Download Manager lists jobs, shows truthful progress/status, exposes cancel and eligible retry, explains failures, permits output-directory choice and opens a completed artifact/folder.
- No pause/resume claim until the engine contract proves it. No locally persisted second source of truth.

## 7. Validation and platform claims

- Build and test the exact supported platform matrix inherited from the existing repository. Do not broaden platform claims just because Electron can package multiple OSes.
- Test the real packaged executable, native Host registration/connectivity, clean install, upgrade over prior candidate, uninstall behavior, destination permissions, restart recovery and Chromium integration.
- Use controlled/authorized fixtures for direct and HLS flows; keep secrets and user browsing data out of test artifacts.
- Bind all validation evidence to one candidate SHA and exact package/installer hashes.
- G0/G1 is a human-owned evidence activity; agents may prepare the protocol but cannot fabricate human sessions.
